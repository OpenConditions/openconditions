# Database migration history reset to a baseline

Affected versions: The first product release containing the baseline and every later one. No product version is assigned by this change.

Action: Create the OpenConditions database afresh. A database created by an earlier build is not upgraded: its migrations fail with "relation already exists". Drop the `conditions` schema, or the whole database, before starting the new ingest service. Earlier builds kept their history in `drizzle.__drizzle_migrations_oc`; it is no longer read and can be dropped too.

Set the new required secret `OPENCONDITIONS_SECRETS_KEY` (or `OPENCONDITIONS_SECRETS_KEY_FILE`, a file holding it) on every service that declares it: the ingest service, the heavy-feeds ingest process, the contributions API and, when federation is enabled, the federation service. A service without it, or with a value that is not a key, stops at start. Generate it once, for `openconditions-ingest`, with `openssl rand -hex 32`, and give the others a copy of that same value, never a newly generated one. The first ingest process to start seals it in `conditions.secrets_key_check`, and every other service refuses to start with a different key. Keep the key in your recovery set: the database holds the OAuth tokens and the private keys only encrypted with it, and a lost key means logging in to every OAuth grant again and taking a new federation identity. Under OpenMapX, OpenMapX's credential vault also holds the key, encrypted with OpenMapX's own secrets key, so keep that key in the recovery set too. See [secrets encrypted at rest](../../README.md#secrets-encrypted-at-rest).

Prepare the database roles before the ingest service first starts. The ingest service's role needs `CREATE` on the database at every start, also once `conditions` exists, because it runs `CREATE SCHEMA IF NOT EXISTS`. The heavy-feeds process and the federation service connect as the ingest service's role. Set the search path of both OpenConditions roles, the ingest service's and the contributions service's, to `conditions, extensions` (`ALTER ROLE … SET search_path = conditions, extensions`; under OpenMapX, PostGIS lives in the schema `extensions`) before the ingest service first starts. OpenConditions sets no search path in code. See [database roles and grants](../database-migrations.md#database-roles-and-grants).

Only the ingest service's processes migrate now, the primary and the heavy-feeds process, and they record the history in `conditions.__drizzle_migrations`. The contributions and federation services wait at start until the schema reaches their version, for at most `OPENCONDITIONS_SCHEMA_WAIT_TIMEOUT_MS` (five minutes by default). While a first migration runs longer than about three minutes, they report unhealthy, and they recover once it finishes.

At every start the ingest service grants OpenMapX's tile role `openmapx_tiles_owner` and the contributions service's role `openconditions_contributions` exactly what they use, each if it exists. Create both before the ingest service first starts; a role created later gets its grants when the ingest service restarts.

The OpenLR resolver's routing graph now lives in its own schema `openlr`; build it again after the upgrade (see below).

Crowd reporters are kept for 12 months after their last enrollment and entitlement end: the ingest service's records sweep then deletes a reporter with its votes, refusals and token quotas, and its evidence stays without its key. Deleting a reporter, by the sweep or by hand, also removes its key from its crowd readings, situations, revisions and federation journal entries. Two exceptions remain: a hand delete shortly after a situation purge can leave journal entries holding the key until the daily journal prune, and the block list keeps a blocked key for as long as the block stands; see the [crowd reporting limitations](../crowd-reporting-limitations.md#privacy-posture). Ended token quotas, spent tokens a day past their issuer key's validity and federation erasure facts past their 30 days are deleted as well. The reporter table no longer has the unused columns `osm_uid`, `email_lookup_hmac` and `flagged_count`, and votes no longer have `subject_component_key`.

Compatibility: The resulting schema differs from the one the earlier migrations produced in these ways:

- Secrets: OAuth tokens and the issuer and federation private keys are stored encrypted, checked against the new `secrets_key_check` table. The columns `oauth_grant.refresh_token`, `oauth_grant.access_token`, `issuer_key.private_key` and `federation_instance_key.private_key` are replaced by `<column>_ciphertext`, `<column>_iv` and `<column>_tag`, each trio with a CHECK named `<table>_<column>_check`.
- Crowd data: the dropped columns and the retention above. New foreign keys to `reporter(key_id)`: `report_evidence_actor_key_id_fkey` (`ON DELETE SET NULL`), and `report_refusal_actor_key_id_fkey`, `sub_claim_key_id_fkey` and `token_quota_key_id_fkey` (`ON DELETE CASCADE`). The new column `spent_token.expires_at timestamptz NOT NULL`. The `sub_claim` unique key covers four columns instead of five (`sub_claim_subject_class_subject_id_key_id_claim_type_key`).
- Functions and triggers: the new functions `conditions.grant_consumer_roles()`, which grants the roles above, and `conditions.reporter_strip_key()`, run by the new `BEFORE DELETE` trigger `reporter_strip_key` on `reporter`.
- Names: every constraint and index is named after its table and columns (`<table>_pkey`, `<table>_<columns>_key`, `<table>_<column>_fkey`, `<table>_<columns>_idx`, `<table>_<what>_check`) or, for partial, collated, expression and over-long indexes, after their purpose; the GeoNet coverage CHECK is now `geonet_coverage_order_check`.
- Ids and types: the five `bigserial` ids are identity columns, with the same sequence names; `jma_budget.day` is a `date`; `segment_observation.confidence` is `confidence_score`; `smn_cap_message.retrieval` has no default.
- Checks: closed value sets are checked (level of service, segment speed confidence, binding status and direction, subscription status, erasure reason).
- Indexes: three indexes that a primary key serves or nothing reads are gone, the crowd evidence index keys on the evidence state alone, and `feature` and `offer` have indexes for the records sweep. The crowd sweep has the new indexes `reporter_last_active_at_idx` and `federation_tombstone_expires_at_idx`, and `spent_token_expires_at_idx` replaces `idx_spent_token_spent_at`.
- Storage: 30 tables have a different physical column order with the same columns, among them `observation`, `observation_latest` and `observation_rollup_hourly`, which store their fixed-width columns first. A `SELECT *` or a `COPY` without a column list sees the new order.
- API: the binding metrics of `/feeds/status` no longer carry `unknownStatus`, since a CHECK now rules out a binding status the reader does not know.

The OpenLR resolver's graph build no longer writes to `conditions`: it creates `osm_nodes` and `osm_lines` in its own schema `openlr`, owned by the role that builds the graph, and the resolver reads them there. A graph built into `conditions` by an earlier build is not read; build it again. The resolver's [README](../../services/openlr-resolver/README.md#database-roles) lists the rights its two roles need.

The traffic tile function `conditions.segment_flow(integer, integer, integer, json)` is unchanged. Data fixes that the earlier migrations applied to existing rows are not part of the baseline, since a new database has no rows to fix.

Caveats: The earlier migration history is preserved in Git up to commit `09e880bd`. See [database migrations](../database-migrations.md) for how schema changes are made from now on.
