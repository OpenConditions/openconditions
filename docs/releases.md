# Product prepare and review

Use **Actions → Product prepare and review** on main. Choose **prepare**, enter a proposed product version and curated release notes, then run it. CI discovers the latest exact-main push and its attempt, checks all main gates and the native four-image producer, builds the pinned public OpenMapX validators in an owned installation, and prepares the exact seven metadata files. A separate narrowly privileged job opens the normal preparation PR and links it in the summary. The run summary leads with source, review artifact, pending readiness and next action. Full identities and JSON stay in the Actions artifact; operators do not transcribe run IDs, digests, local tool paths or passing readiness JSON.

If current main CI is pending or failed, preparation blocks with a diagnostic. It does not silently choose an older green source, PR artifact or fork. No actual version or run is selected merely by merging this workflow source. Network dependency acquisition is an explicit CI setup step using frozen locks and lifecycle-disabled installs; developer Mac caches are not a prerequisite. Validator source, packed package, resolved dependency and admission bytes must match the reviewed pins. Reproducibility differences fail with retained diagnostics rather than weakening admission.

## The two source events

A is the fully qualified main source that built the original images. Preparation creates metadata proposing those exact image bytes. B is the later main commit containing the reviewed preparation. They are different events: green A or a green preparation PR cannot qualify B. After a normal preparation PR has been reviewed and merged, run **review** for its committed version. CI discovers B's latest exact-main push, reads A's identities from passive committed metadata and independently verifies them through the native producer. It checks exact JSON-pointer restrictions, unchanged actual four-image BuildKit contexts, original provenance, expiry and fresh native readbacks. Images remain built from A; the eventual tag target B is data only.

The preparation PR job owns the reserved `release/prepare-<version>` branch. It reads only the digest-bound artifact from this successful validation job, rechecks current main, native image evidence, artifact eligibility and version history, and constructs a Git tree changing exactly the seven verified paths from A. Existing output is never rebased or force-pushed. An identical open bot PR and exact branch may be reused; orphan/human branches, different content, closed PRs and changed source stop. Failed or unknown writes stop without automatic retry, rollback or deletion of partial resources.

Review the linked PR and its curated notes. GitHub may not start required checks for a `GITHUB_TOKEN`-created PR: a maintainer must approve/run normal PR checks if the platform requires it. The workflow does not dispatch a hidden workaround, approve or merge. Repository/organization policy must also permit Actions to create PRs; job-level write permissions cannot override that separate GitHub setting. Source delivery does not enable it. A policy rejection stops without retries or cleanup of partial reserved resources; a maintainer must inspect the result before retrying. After review and user merge, choose **review** with the committed version.

## What reviewers see

The Actions artifact contains the seven metadata files and preparation evidence, or the post-merge review bundle with extension/services, curated notes, qualification, original artifact references, actual portable/admission results and exact byte/mode inventory. Image/SBOM/scan archives retain their original immutable native identities; they are not rebuilt or repacked as B. Unknown paths, source, digest, mode, symlink, partial sets, changed policies and expired/substituted evidence fail closed. Exact diagnostic JSON is for inspection and expert recovery, not normal operator input.

Default services remain ingest and contributions-api. Heavy ingest and federation remain opt-ins. Environment, configuration/schema, networking, capabilities, licensing and membership are frozen by the release-only metadata contract; an ordinary earlier source PR and new qualified A are required for those changes. OpenMapX validation uses actual pinned public source and package contents, not copied schemas, npm availability assumptions or modifications to an active OpenMapX checkout.

## Readiness is pending, not invented

Missing readiness evidence does not prevent a review artifact. It does prevent publication acceptance. Every bundle retains `releaseAuthority: false` and `readinessExecution: BLOCKED_NO_TRUSTED_PRODUCER`. Structurally valid JSON, hashes, a summary or fixture tests cannot prove operational execution.

The pending checklist requires actual clean installation/configuration and health, representative fixtures with rights/privacy, upgrade and schema migration from an identified real prior deployment, backup/restore/recovery, optional federation/TUF compatibility and supported PostgreSQL/platform execution. Externally keyed/live providers need separate evidence. Existing PG16/PG18 test cohorts do not create a new production-support policy. The expert readiness transport schema still validates candidate/prior deployment/tool/time/evidence bindings, but operators are not asked to invent passed claims. A trusted readiness producer and maintainer judgment remain unimplemented prerequisites.

## Publication remains unavailable

Validation has only read permissions and standard artifact upload. Only the separate successful-prepare PR job has contents/PR write permissions; review never runs that job. It can create a preparation branch/PR and add Medformatik and existing labels, but cannot approve, merge or publish. There is no GitHub draft, release, tag, registry image, npm version, channel or host operation. Product and package releases remain independent. Protected publication approval, future-release immutability, operational rehearsal, identity-based partial-publication recovery and channel promotion require later reviewed implementation and separately authorized execution. There is no placebo publish button.

Promote the originally qualified A bytes without rebuilding only after those stages exist and approval has been given. Conflicting published assets must never be overwritten. Preview advances only after coherent publication; missing preview or an exact version fails rather than falling back to main. Stable remains absent. History/alias transition and actual next unused version selection remain later decisions. Native rereads are not atomic with any future operation, and artifact expiry cannot be renewed by local claims.
