# Product prepare and review

Use **Actions → Product prepare and review** on main. Choose **prepare**, enter a proposed product version and curated release notes, then run it. CI discovers the latest exact-main push and its attempt, checks all main gates and the native four-image producer, builds the pinned public OpenMapX validators in an owned installation, and prepares the exact seven metadata files. A separate narrowly privileged job opens the normal preparation PR and links it in the summary. The run summary leads with source, review artifact, pending readiness and next action. Full identities and JSON stay in the Actions artifact; operators do not transcribe run IDs, digests, local tool paths or passing readiness JSON.

If current main CI is pending or failed, preparation blocks with a diagnostic. It does not silently choose an older green source, PR artifact or fork. No actual version or run is selected merely by merging this workflow source. Network dependency acquisition is an explicit CI setup step using frozen locks and lifecycle-disabled installs; developer Mac caches are not a prerequisite. Validator source, packed package, resolved dependency and admission bytes must match the reviewed pins. Reproducibility differences fail with retained diagnostics rather than weakening admission.

## The two source events

A is the fully qualified main source that built the original images. Preparation creates metadata proposing those exact image bytes. B is the later main commit containing the reviewed preparation. They are different events: green A or a green preparation PR cannot qualify B. After a normal preparation PR has been reviewed and merged, run **review** for its committed version. CI discovers B's latest exact-main push, reads A's identities from passive committed metadata and independently verifies them through the native producer. It checks exact JSON-pointer restrictions, unchanged actual four-image BuildKit contexts, original provenance, expiry and fresh native readbacks. Images remain built from A; the eventual tag target B is data only.

The preparation PR job owns the reserved `release/prepare-<version>` branch. It reads only the digest-bound artifact from this successful validation job, rechecks current main, native image evidence, artifact eligibility and version history, and constructs a Git tree changing exactly the seven verified paths from A. Existing output is never rebased or force-pushed. An identical open bot PR and exact branch may be reused; orphan/human branches, different content, closed PRs and changed source stop. Failed or unknown writes stop without automatic retry, rollback or deletion of partial resources.

Review the linked PR and its curated notes. GitHub may not start required checks for a `GITHUB_TOKEN`-created PR: a maintainer must approve/run normal PR checks if the platform requires it. The workflow does not dispatch a hidden workaround, approve or merge. Repository/organization policy must also permit Actions to create PRs; job-level write permissions cannot override that separate GitHub setting. Source delivery does not enable it. A policy rejection stops without retries or cleanup of partial reserved resources; a maintainer must inspect the result before retrying. After review and user merge, choose **review** with the committed version.

## What reviewers see

The Actions artifact contains the seven metadata files and preparation evidence, or the post-merge review bundle with extension/services, curated notes, qualification, original artifact references, actual portable/admission results and exact byte/mode inventory. Image/SBOM/scan archives retain their original immutable native identities; they are not rebuilt or repacked as B. Unknown paths, source, digest, mode, symlink, partial sets, changed policies and expired/substituted evidence fail closed. Exact diagnostic JSON is for inspection and expert recovery, not normal operator input.

Default services remain ingest and contributions-api. Heavy ingest and federation remain opt-ins. Environment, configuration/schema, networking, capabilities, licensing and membership are frozen by the release-only metadata contract; an ordinary earlier source PR and new qualified A are required for those changes. OpenMapX validation uses actual pinned public source and package contents, not copied schemas, npm availability assumptions or modifications to an active OpenMapX checkout.

## Disposable rehearsal and remaining readiness

Review automatically runs representative rights/privacy integration fixtures against owned databases, then starts the exact candidate ingest and contributions-api image bytes on an isolated internal Docker network with synthetic configuration and remote feeds disabled. It checks actual health and bundled migrations, stops each service, backs up the migrated schema using PostgreSQL `pg_dump`, drops that schema in its disposable database, restores with `pg_restore`, and checks the synthetic data and restarted service health. The artifact retains per-service runtime and cleanup results alongside the candidate A/B identities. These commands never accept an operator database URL. A failed command, incomplete cleanup or changed/expired native evidence fails the review; partial diagnostics are retained.

The rights/privacy fixtures exercise source behavior, separately from the candidate-image runtime checks. They do not establish every provider or privacy contract. The PostgreSQL 16/Linux amd64 rehearsal cohort is inherited from image qualification and does not define production platform support. No actual prior deployment has been identified: upgrade/migration from production stays pending, and synthetic migration fixtures cannot replace it. Optional federation/TUF behavior and live provider checks remain unqualified.

Missing external readiness evidence does not prevent a review artifact. It does prevent publication acceptance. Every bundle retains `releaseAuthority: false` and `readinessExecution: BLOCKED_NO_TRUSTED_PRODUCER`. Structurally valid JSON, hashes, a summary or fixture tests cannot prove operational execution.

The pending checklist requires actual clean installation/configuration and health, representative fixtures with rights/privacy, upgrade and schema migration from an identified real prior deployment, backup/restore/recovery, optional federation/TUF compatibility and supported PostgreSQL/platform execution. Externally keyed/live providers need separate evidence. Existing PG16/PG18 test cohorts do not create a new production-support policy. The expert readiness transport schema still validates candidate/prior deployment/tool/time/evidence bindings, but operators are not asked to invent passed claims. A trusted readiness producer and maintainer judgment remain unimplemented prerequisites.

## Protected publication source and blockers

Review now reports publication eligibility separately from review success. The separate `publication` job names the `product-release` environment and has only contents/packages write and Actions read. Validation remains read-only; preparation PR writes remain isolated. A missing protection or execution authority does not request an approval: eligibility stays false and the publication job is skipped. This source does not create an environment or enable immutable releases.

The proposed environment requires Medformatik, permits self-review under the existing single-maintainer policy, forbids administrator bypass and permits only the main branch. The preflight checks the reviewed main ruleset, exact main source, native [reviewer/environment identity](https://docs.github.com/en/rest/actions/workflow-runs#get-the-review-history-for-a-workflow-run) and immutable-release status. GitHub’s [immutable-release status API](https://docs.github.com/en/rest/repos/repos#check-if-immutable-releases-are-enabled-for-a-repository) requires Administration read; `GITHUB_TOKEN` cannot request that permission. No alternate credential or local variable substitutes for this readback. That capability gap needs a separately reviewed resolution before live execution.

Full operational readiness also lacks a trusted producer. The bounded default-service rehearsal cannot prove an actual prior-deployment upgrade, optional federation/TUF, every rights/privacy contract or operator/platform acceptance. Structurally valid claims and protected approval cannot fabricate those effects. The production entrypoint therefore refuses writes even if a local JSON file says passed. There is no runnable publication path until these authorities are supplied through reviewed source; the source primitives and owned adapter tests do not establish native GitHub or GHCR acceptance.

The publication primitives validate an explicit complete asset set: exact extension/service/candidate metadata and curated notes, qualification and portable/admission reports, original image provenance, actual SBOM/scan/qualification bytes and execution evidence. A review bundle containing references alone is insufficient. The manifest binds A, B, tag target B, original image digests and immutable artifact identities, asset byte hashes and expiry. It grants no authority by itself.

Owned tests exercise copying the original OCI blobs and platform manifest without rebuilding, staging all draft assets and verifying their bytes/digests, publishing an immutable prerelease targeting B, then moving preview last. Identical completed resources are read back; conflicting tags, version digests, assets or release identity stop. Failed or unknown writes stop without automatic retry, rollback or deletion; inspect native state read-only before another authorized attempt. Only the same unexpired candidate may resume. A final read/write race remains: preflight reads are not atomic with GitHub or registry writes. Published assets are never overwritten, and incomplete image/asset publication never advances preview. The four preview tags move sequentially after the complete immutable release is confirmed; an interruption can leave mixed preview versions. Inspect their native digests read-only, then resume only the same unexpired candidate to finish the remaining updates. There is no cross-repository transaction or automatic rollback.

Main remains development. Existing latest/history consumers are unchanged; stable is never moved implicitly. Missing preview or an exact version must fail clearly rather than fall back to main. Actual environment/immutability activation, readiness authority, approved end-to-end rehearsal and deliberate publication remain separate steps. No real version, tag, release, registry or host operation occurs merely by merging this source. Product publication never publishes npm packages.
